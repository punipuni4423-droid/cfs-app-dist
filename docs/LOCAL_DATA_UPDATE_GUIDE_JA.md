# ローカル保存の更新と旧版移行

新版の業務データと共同編集状態は、通常ランチャーが指定する `CFS_APP_DIR/data` に保存します。開発実行でこの変数が未指定の場合は従来どおり作業ディレクトリの `data` を使います。指定する場合は絶対パスが必要です。データ形式や保存・復旧プロトコルは変更しません。

通常のコード更新はアプリの書き込みプロセスを停止し、`data` 全体を `artifacts/data-recovery/local-data-日時-ID/canonical` へコピーします。projects、trash、transaction journal、共同編集情報、認証ファイル、未知の追加ファイルを含み、ファイルのサイズ・SHA256と空ディレクトリを再照合します。manifestはパスとハッシュだけを記録し、認証秘密の本文を含みません。バックアップ自体は認証ファイルを含むため非公開で保管してください。検証失敗時は更新を停止し、部分バックアップも残します。ドキュメントのみの更新は従来どおり再起動しません。

## 旧版の初回移行

旧版には `.next/standalone/data` または `runtime/data` に保存するものがあります。旧updaterは実行開始時の処理を保持し、更新後の新scriptを読み直しません。旧版のUpdateボタンだけではこのデータを保護できません。旧版利用者は新しい移送scriptと保全helperを同じ管理用フォルダへ取得し、初回更新前に明示メンテナンスを行います。インストール済みの追跡ファイルを手編集しないでください。

1. 対象AppDir、実サーバーの起動entry、ポート、local保存モードを確認します。共有Supabase案件は本手順の対象外です。ローカルに残ったJSONを共有案件の原本として移送しないでください。
2. 全利用者が保存を終えたことを確認し、エディター・自動再起動サービス・ランチャーを閉じ、作業完了まで再起動を禁止します。別ポートの同一インストールも対象です。補助は対象AppDirをcommand lineに持つNode writerを停止し、対象ポートの不明なプロセスには触れず拒否します。独自の相対パス起動や外部writerは運用担当が停止を確認してください。
3. 下記例のAppDirとポートを対象に合わせて、管理用フォルダの補助を実行します。`LegacyStore` は実際の旧保存先が `.next/standalone/data` なら `standalone`、`runtime/data` なら `runtime` です。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\migrate-cfs-legacy-local-data.ps1 -AppDir 'C:\Apps\CFS' -Port 3014 -LegacyStore standalone -LocalModeConfirmed -RunOfficialUpdater
```

4. 補助は停止状態でrootと旧保存先の原本全体を別世代へバックアップします。rootが空なら旧一式を非上書きコピーし、両方が完全に同じなら何も書き換えません。rootと旧保存先に差がある場合（片方だけのファイルも含む）、壊れたJSON、複数旧保存先、junction等の再解析ポイントは拒否します。最新日時で選別したり、projectsとtrashを別々にマージしたりしません。原本の移動・削除は行いません。
5. 照合成功後、旧サーバーを再開せずインストール済みの公式updaterを直接実行します。これは「事前移送＋公式更新worker」の経路で、Update UIだけの操作ではありません。`-RunOfficialUpdater` を省略した場合は停止したまま終了するので、古いアプリを再開せず公式updaterを実行してください。
6. 更新完了後はlocal/remote/build SHA、案件・ゴミ箱・履歴の読戻し、通常保存→再読込、新しい書き込みがroot `data` に入ることを確認します。照合が終わるまでバックアップを保持します。

## 拒否・失敗時

移送中の拒否はサーバーを自動再開しません。エラーに表示された世代のcanonical/legacyと、残された両原本を確認します。途中コピーでrootが一部だけできた場合も自動削除しません。選択した一式を別途レビューし、整合する組全体を保全したうえで担当者が復旧します。差のある組を手順の再実行で上書きしないでください。

Git更新前に拒否され、旧保存先の原本が変更されていないことを確認できれば、メンテナンスを中止して通常ランチャーで旧版を再開できます。その場合は移送済みrootと旧版の保存先が再び分岐し得るため、次回更新前に再棚卸しが必要です。公式updater開始後の失敗は `artifacts/self-update/status.json` とログで現在SHA・build・起動先を確認してから対応してください。updater自身が旧ランタイムを再開する場合もあります。新版の書き込み開始後に旧バックアップを単純上書きしてはいけません。

停電・外部writer・保全中のフォルダ差替えをこの補助だけで完全に排除するものではありません。停止確認から更新終了まで、対象インストールの排他的メンテナンスを維持してください。
