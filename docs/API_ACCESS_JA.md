# PC・タブレットの接続認証

T-108 / T-144。T-144のポート別Cookieは次回配布向けの実装仕様。

PCは既存のCFSランチャーから起動する。ランチャーはローカルの鍵を使って5分有効の初期リンクを開く。リンクはブラウザでセッションに交換し、アドレスから資格情報を取り除く。セッションはhttpOnly・SameSite=Strict cookieで90日保持する。HTTPS時はSecure属性も付く。確立済みブラウザは、通常のlocalhostブックマークから開ける。

Cookie名は `cfs-access-v2-p<port>`（例: `cfs-access-v2-p3014`）。同じホストの別ポートで異なるインストールへ接続しても上書きしない。Hostに明示された整数ポート（1〜65535、IPv6は角括弧付き）を検証し、`PORT`環境変数があれば一致を要求する。不正・欠落・不一致は401で拒否し、既定ポートへ補完しない。転送ヘッダーから名前を作らない。ポート分離はCookieの取り違え対策で、署名・期限・権限の検証は引き続き必要。

読取順は `x-cfs-access-token` → 当該ポートの新名 → 旧 `cfs-access-v1`。上位候補が空・改竄・別鍵・期限切れなら401となり、下位候補へ降格しない。選択対象の同名Cookieが複数なら拒否し、他ポート名は探索しない。ヘッダーがある場合はCookieを読まない。`sessionToken(request)` と `readSession(token, keys)` の呼出し形式、SupabaseのAuthorizationヘッダーは維持する。

旧名のみの有効セッションは `GET /auth/connect` で同じトークンを新名へ昇格する。userId/sessionId/role/expは変更せず、Max-Ageは残存期限以内とする。旧Cookieは書換え・削除しない。POSTは新名だけを書き、同ロールの有効な既存セッションは維持する。失効・別鍵Cookieが残った場合も、有効なlauncher grantで新たに接続し直せる。CookieのPathは `/`、保持期間は最大90日で、既存セッションの再利用で有効期限を延ばさない。

旧名の読取期限は `apiAuthCore.mjs` の `LEGACY_COOKIE_READ_UNTIL` で固定する。**確定値 `2026-12-24`（版 26.9.2 の公開予定日 2026-09-25 + 90 日。UTC 00:00 以降は旧名を読まない）。** 次に公開日がずれた場合はリリース担当が再確定する。 再起動で延長しない。期限後、旧Cookieの上書き、同一ポートで別鍵のインストールへ切替えた場合はlauncherから再接続する。既に開いている旧クライアントの自動昇格は保証せず、未保存内容を保全して通常の再読込を行う。旧版へ戻す場合、新名だけの接続は再接続が必要になる。

未認証または期限切れの場合は接続画面が表示される。PCはランチャーから開き直し、タブレットはPCで発行した接続リンクを開き直す。タブレットへの招待リンクは1日有効で、端末ごとに別の利用者IDとセッションが発行される。リンクを知る人は編集用セッションを得られるため、接続先の利用者に渡す。タブレットには自己更新・強制ロック解除・招待発行の権限を与えない。QRコードを使う場合も同じリンクを使用する。外部QRサービスへのリンク送信は行わない。

全15 APIルートの公開GET/POSTは認証必須。localhost・Host・転送ヘッダーによる免除はない。既存のCSRF判定とSupabaseの認証・権限判定は残る。ローカル利用者IDはセッションのサーバー発行IDと一致する必要があり、編集セッションIDはそのセッションに属するタブ識別子を使う。SupabaseのBearerヘッダーと追加のローカル認証は併用する。

鍵は `CFS_AUTH_DIR/access.json`、未指定時は `CFS_APP_DIR/data/auth/access.json`（CFS_APP_DIR未指定時は作業フォルダ）に初回生成する。破損した鍵を勝手に再生成しない。このファイルはGit・共有パッケージに含めず、値をログや証跡へ出力しない。鍵の変更で既存リンクとセッションは無効になる。HTTPのLAN通信は従来どおりで、暗号化を追加したわけではない。

PC限定で待ち受ける場合は、起動前に `CFS_LOCALHOST_ONLY=1` を設定する。既定は従来のLAN待ち受け。自己更新による再起動もこの設定を引き継ぐ。

ごみ箱GETは `updatedAt` を返し、ローカル保存POSTは同じ値を `expectedUpdatedAt` に含める。既存ファイルに世代がない場合の初期値は空文字。保存処理はディレクトリロック内で世代比較・検証・置換を行い、競合は409/TRASH_CONFLICTで拒否する。競合時に全件を勝手にマージせず、再読込してから操作をやり直す。ロック取得の待ち時間は5秒、遅い稼働中処理のロックを自動で奪わない。Supabaseごみ箱の保存処理は既存のEdge Functionに委譲する。

## 隔離検証

Playwrightでは `PLAYWRIGHT_BASE_URL=http://127.0.0.1:3087` のように3086〜3095を明示し、専用 `CFS_AUTH_DIR` をサーバー・テストで共有し、`CFS_TEST_AUTH=1` を設定する。テスト設定が専用の認証cookieを渡す。実データ操作は従来どおりモックする。匿名検査ではstorageStateに空cookieを明示する。

`_api_access_ports.spec.ts` は別の実サーバーを `CFS_PORTS_PEER_URL` / `CFS_PORTS_PEER_AUTH_DIR` で指定する。両方とも同一ホストの異なる隔離ポートとし、別CFS_APP_DIR・data・auth・NEXT_DIST_DIR、localモードで起動する。合成データだけでCookie認証と保存→GETを確認し、ヘッダー認証・auth mockは使わない。起動したハーネスが所有プロセス停止・listener解放・合成data/authの削除を行う。
協調機能は既定の有効状態で実行でき、`CFS_COLLABORATION_ENABLED=false` は不要。specがCookie認証済みの`/auth/connect`から得たIDで合成ユーザーを登録し、保存時に同セッションのidentityヘッダーを付ける（access-tokenヘッダーによる認証代替ではない）。

CLIクライアントはローカルの `node scripts/cfs-access.mjs session` の出力を `x-cfs-access-token` に渡せる。出力は秘密のため表示・ログ保存しない。APIの無認証化やテスト用バイパスは設けない。ランチャー・起動確認・共有パッケージのスクリプト一覧もこのCLIに追随している。
