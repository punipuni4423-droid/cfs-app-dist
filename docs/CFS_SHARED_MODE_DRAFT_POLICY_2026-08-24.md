# 共有モードのブラウザ下書きポリシー（2026-08-24）

## 背景（インシデント）

2026-08-24、共有プロジェクトの特定ルームタイプが複数回「古い状態」に巻き戻る事象が発生した。

原因は共有（Supabase）モードのブラウザ下書きの扱い:

1. 編集のたびに 1.2 秒デバウンスでブラウザ localStorage に下書きが保存される（認証チャーン対策）。
2. リロード時、「下書きの updatedAt がサーバーより新しければ下書きを黙って採用」していた。
3. 古いサーバー状態をベースに編集した端末は、下書きが常に「新しい」ため、リロードしても古いデータが復活し、その後の保存で他ユーザーの編集やサーバー側の修正を上書きしてしまう。

## 新しい動作（app/page.tsx）

- **共有（supabase）モード**: サーバーを常に正とする。
  - リロード時にサーバーより新しい下書きが残っていた場合、その下書きを
    `<プロジェクト名>_unsaved_browser_draft_...json` として自動ダウンロードし、
    localStorage から削除した上で、サーバーの最新データを表示する（アラートで通知）。
  - 必要な場合は Import Data からバックアップを取り込んで復元できる。
- **ローカルモード**: 従来どおり（新しい下書きを採用。単独利用でのクラッシュ復旧を優先）。

## 変わらないもの

- 明示的な保存の競合検出（`Project was updated by another user.`）と
  バックアップ / リロード / 上書きの選択フロー。
- サーバー読み込み失敗時のローカルフォールバック（本当のサーバー障害時のみ）。
- 編集中のブラウザ下書き保存そのもの（リロードまでのクラッシュ保険として保持）。

## 既知の残課題

- 一括保存 RPC `save_cfs_project_set` には楽観ロック（expectedUpdatedAt）がなく、
  編集ロック保持者の一括保存はサーバー内容を無条件に置き換える。
  今回の修正でリロード時の古い下書き復活は根絶したため実害は大きく低下したが、
  将来的には per-project の expected 比較を RPC に追加するのが望ましい。
